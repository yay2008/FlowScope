# DOM、流动性热力图与成交明细规划

状态：待实施的功能方案。日期：2026-10-23。范围：国内期货、币安与 OKX USDT 永续，按数据能力分级。本文基于当前工作区代码审阅，未新建行情连接，也未验证当前账户的实际行情权限。

## 1. 产品目标与布局

将三个视图组成一个「订单流工作台」，围绕同一实际合约、同一时间游标和同一价格选择协同工作：DOM 看当前可见挂单，热力图看可见挂单随时间的变化，成交明细看已发生的成交或快照成交增量。

顶栏增加「双图 / 订单流」布局切换。订单流布局中，主区域为「热力图 / 足迹」切换，右侧为 DOM 和成交明细；保留现有合约选择、自选、指标与模拟交易入口。默认在订单流布局收起自选，给价格视图留空间。

- 宽屏：主图约 60%，DOM 约 22%，成交明细约 18%；分隔条可调整。需要背景图时可展开一块较小的现有 K 线图。
- 中等宽度：主图与 DOM 并排，成交明细放下方。
- 窄屏：主图在上，DOM / 成交明细在下方切换；不把三个面板压缩到无法阅读。
- 顶部持续显示实际合约、交易所、数量单位、数据档位、成交口径和连接状态。主连代码另显示当前实际月份。
- 主图与 DOM 使用同一价格网格；成交明细点击可定位主图时间和价位。DOM 点击用于选择和定位价位；现有模拟交易仍使用自己的入口。
- 「暂停跟随」只暂停画面，采集继续；返回实时跳到最新。查看历史时三个面板共同使用历史游标，并明确显示「回放」和该时刻。不能让历史主图旁边仍显示未标明的实时 DOM。

## 2. 现有能力与数据分级

| 来源 | 当前代码可复用 | 首版可承诺的功能 | 必须表达的边界 |
| --- | --- | --- | --- |
| 国内期货 / TqSdk | `ingest.py` 的 Quote、Tick 与实际月份映射；`tick_analytics.py` 的快照增量判向 | 按实际权限展示一档或多档 DOM；有限深度历史热力图；快照成交增量列表 | 不承诺所有合约都有五档；成交方向为估算，区间成交量不能当成一笔真实成交 |
| 币安 USDT 永续 | `binance_feed.py` 的 `depth20@100ms`、`aggTrade` | 20 档 DOM、近盘口热力图、聚合成交明细 | 聚合成交记录不等于原始逐笔撮合；20 档以外的数据是未知 |
| OKX USDT 永续 | `okx_feed.py` 的 `books` 400 档重建、序号连续性检查、`trades-all`，数量已折成币 | 可选显示档位的 DOM、较宽价格范围热力图、逐笔成交明细 | 400 档仍非全市场所有订单；缺序时沿用作废与重同步机制 |
| 多所汇总 AGG | `crypto_aggregate.py` 的来源关系 | 成交明细可按交易所筛选；DOM 与热力图先选择具体交易所 | 不能把两家盘口直接伪装成一个可成交的订单簿；不同交易所时间戳不存在精确的全局成交先后 |

TqSdk 官方 Quote 字段包含买卖一至五档，但字段定义不能证明当前账户和合约实际提供全部档位；运行时应检查有效值和数据源能力。[Quote 字段说明](https://doc.shinnytech.com/tqsdk/latest/reference/tqsdk.objs.html)

关键代码事实：

- `crypto_feed.py::_apply_event` 当前将盘口替换进最新报价缓存，尚未积累盘口时间序列。
- 当前 WebSocket `/ws` 围绕合约、K 线周期、买卖量口径和足迹组织，不适合直接混入全部高频成交和深度消息。
- `ingest.py::Feed.data_changing` 未把盘口价量变化作为独立展示事件处理；新增 DOM 需要直接观察 Quote 的盘口字段，不应等待 K 线重算。
- 加密成交会进入多个原生周期 Feed；新事件通道须在按周期分发前去重、发布一次，避免成交明细重复。
- 原有大额成交检测器包含筛选、合并和保留上限，不能充当完整成交明细库。

## 3. DOM 首版

### 展示

中间为价格阶梯，两侧为买挂量和卖挂量；可选增加最近 5 秒主动卖出 / 主动买入成交列。买卖方向同时用文字和颜色区分。期货成交列明确标注估算，并允许关闭。

- 最优买卖价、最新成交价、价差，价差同时显示 tick 数。
- 买卖深度条与数量；顶部显示各自可见总量。
- 档位净变化：同一价位相较上次有效观测的数量变化。名称使用「挂量净增减」，不标成确定的新增委托或撤单。
- 深度失衡：`(买方可见量 - 卖方可见量) / (买方可见量 + 卖方可见量)`；同时注明统计档数或价格范围，分母为零或任一侧不可用时显示不可计算。
- 大挂量强调采用本合约此前的分位基线；预热不足时只显示原始数量，不输出异常判断。
- 默认显示买卖各 10 档，按能力允许 1 / 5 / 10 / 20 / 50 档；可见行数与源数据档位分开。只有一档时不能把其他价位填成零。
- 支持 1 / 5 / 10 个最小价位的价格合并、自动居中、手动定位、返回最新价。

### 状态处理

价格超出已有深度范围时显示「范围外」；已知有效价位确实没有挂量时才显示零。重连待快照时显示「同步中」，历史数值可以保留为灰色背景，但不能继续充当有效盘口。休市与连接故障分别显示。

只有市场按价格汇总的深度时，无法识别个人订单、队列位置、撤单原因或冰山单身份。即使补充成交，也不能把每一次挂量减少完全归因为成交或撤单。

## 4. 成交明细首版

### 字段与口径

基础列：时间、价格、数量、主动方向；展开列：名义金额、交易所、来源记录编号、原始 / 合并口径。

- 期货：名称为「成交增量 · 估算」。每条显示快照区间的成交增量、区间末价、估算方向；可选显示持仓量变化。不能暗示区间全部成交发生在末价，也不据此标注多开、空开等确定的开平类型。
- 币安：名称为「聚合成交」。保留交易所聚合记录身份；若未来需要构成成交编号范围，需在适配器保留原始字段。
- OKX：名称为「逐笔成交」。沿用 `trades-all` 的主动方向和编号，保留原始张数、合约面值与折算币数量以便核对。
- 来源记录编号按字符串传输，避免 JavaScript 大整数失真。未知方向单独显示，不强行归入买卖。

### 交互

- 按主动方向、数量、金额、交易所过滤；支持「仅大额」快捷过滤并复用现有门槛配置。
- 支持原始来源记录 / 事件合并两种视图。合并视图复用现有同毫秒、同方向、编号连续规则，显示合并条数；跨价位时展示价格区间或加权均价，不称为已确认的单个订单。
- 最新记录置顶；暂停滚动后显示新增条数；恢复时可选择跳到最新。
- 点击记录定位主图时间与价位，并取该游标时刻有效的盘口。期货选择的是快照区间，交互中保留这一点。
- 大额筛选只影响显示，不改 CVD、足迹和统计总量。数量与金额阈值按期货 / 加密、合约和单位分别保存。
- 统计最近 1 / 5 / 30 秒成交量、主动买卖占比与来源记录到达率。跨来源不将记录条数比较成真实成交笔数。
- 列表使用窗口化渲染；按唯一游标翻页，相同毫秒内多条记录不得漏页或重复。

## 5. 流动性热力图

### 首版图层

横轴是时间，纵轴是绝对价格；背景强度表达可见挂量，不表达成交量。可叠加最佳买卖价、最新价和成交气泡；气泡表示成交，背景表示挂单，两者图例和单位分开。

- 默认最近 10 分钟，可选 1 / 5 / 15 / 60 分钟及已有历史范围。
- 价格分组与 DOM 联动；纵向平移、缩放、跟随最新价格。
- 默认按币数量或手数着色，可切换名义金额；同图范围内保持统一单位。
- 显示「相对强度 / 固定数量刻度」；相对刻度采用已过去的样本分位或 `log1p` 压缩，并限制自动调整速度。回放基线不得使用游标以后的数据。
- 悬停或选择一个格子，显示时间段、价格区间、代表挂量、峰值、覆盖比例；避免把聚合格子的平均值叫作一笔真实挂单。
- 成交气泡按同价位、同方向的小时间桶聚合，面积对应数量；买卖方向分开。期货快照增量默认不画成精确成交价气泡，可选空心估算标记并显示区间属性。

### 历史与缺失语义

- 盘口历史从本功能开始记录时积累。已有 OHLCV、足迹或成交历史不能反推出过去盘口。
- 记录数据源实际提供的状态变化，显示分辨率与采集分辨率分离。默认展示使用 250 毫秒或 1 秒桶，远期视图使用更粗聚合。
- 聚合优先保存有效时间内的时间加权平均挂量，同时保留峰值、末值、有效覆盖时长。价格分组合并数量；时间分组不能把重复快照数量累加成虚假挂量。
- 只在连接有效、书本连续、价格仍在该侧可观察范围内时延续最近状态。中断、重同步、休市、换月、深度边界变化和数据淘汰都要形成明确边界。
- 深度以外画「未知」底纹；断线区间留空并标明原因，不能画为挂量归零或把断线前的挂单一路延续。
- 价格坐标固定在绝对价位。盘口移动时不按第几档拼热图，避免把不同价格的挂量误接成一堵墙。

币安首版使用已接入的 20 档，只覆盖近盘口范围。扩大范围时再使用 REST 深度快照加增量流，严格按交易所规定衔接更新编号、检查连续性并在缺序后重建。[币安本地订单簿规范](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly)

## 6. 共用数据层与接入点

建议增加独立的 `OrderFlowHub`，以「交易所 + 实际合约」组织数据，不随 K 线周期复制。不同来源保留自己的成交语义，不用统一字段掩盖数据精度差异。

```text
TqSdk Quote / Tick ──┐
Binance book/trade ──┼─ 来源标准化与能力描述 ─ OrderFlowHub
OKX book/trade ──────┘                         ├─ 当前盘口 + 成交环形缓存
                                             ├─ 追加存储 + 热力聚合
                                             └─ 独立订单流 WS ─ DOM / Tape / Heatmap
现有 K 线与足迹通道 ───────────────────────────── 联动时间和价格选择
```

### 能力与事件

能力至少包含：`bookMode`、源档数、当前有效档数、更新粒度、`tradeKind`、方向是否估算、数量单位、最小价位、可回放区间及缺失原因。

每个事件包含来源、实际合约、来源时间、本地接收时间、会话标识、来源序号或编号、进程内事件序号、有效状态。纳秒时间不直接作为普通 JavaScript Number 传输；使用字符串，展示层转换为毫秒。价格使用整数 tick 或 Decimal 标准化，数量保留源精度和单位。

- 盘口事件明确区分全量快照、增量和作废。源快照只代表其覆盖范围，边界外不可推断。
- 成交事件区分 `trade`、`aggregate_trade`、`snapshot_volume_delta`；后者额外带区间起止和末价。
- DOM 的档位净变化从有效连续状态计算，重连首个快照不产生「大幅加单」信号。
- TqSdk 数据在现有 `wait_update()` 采集线程内读取和复制成不可变事件，不从 WebSocket 线程直接读取持续变化的 Quote / DataFrame。
- 在 `crypto_feed.py::_apply_event` 按周期分流之前发布一次成交事件；盘口在验证成功后发布。保留 OKX 原有重同步与币安源语义。
- 主连换月时按实际合约切换会话，清理当前选择并显示换月分界。两个实际合约的盘口、基线和成交记录不能混接。

### 接口建议

以下为拟新增接口，当前未实现：

- `GET /api/orderflow/capabilities?symbol=...`
- `GET /api/orderflow/snapshot?symbol=...`
- `GET /api/orderflow/trades?symbol=...&before=...&limit=...`
- `GET /api/orderflow/heatmap?symbol=...&from=...&to=...&resolution=...&priceStep=...`
- `GET /api/orderflow/book-at?symbol=...&cursor=...`
- `WS /ws/orderflow?symbol=...&channels=book,trades,heatmap`

独立 WS 使高频数据不挤占现有 K 线推送。沿用先登记订阅、再取一致快照、之后按版本衔接的机制；标识会话边界。盘口可合并展示更新，成交通过批次推送、去重和游标续传保证不静默漏行。慢客户端超过边界时明确要求重新同步，并返回缺失区间。

建议新增 `orderflow.py`、`orderflow_store.py`、`static/orderflow-workspace.js`、`static/dom-view.js`、`static/tape-view.js`、`static/heatmap-view.js`、`static/orderflow.css`。在 `app.py` 接路由，`static/app.js` 接布局和联动；新热力渲染器与现有足迹渲染器分开，通过时间/价格接口协调。

## 7. 采集、存储与性能

- 默认只为正在查看的订单流合约登记深度需求；同合约多视图共享订阅。用户可以明确开启少量合约的后台记录，不能因打开工作台便为全部自选录制深度。
- 采集线程只做校验、标准化与入队；落盘、压缩和远期聚合由单独工作线程处理。队列有界，过载必须记录缺口和原因。
- 追加记录按交易所、实际合约、日期分区；保存周期性盘口检查点及检查点间的更新，历史定位无需从全天起点重放。
- 首轮先录制 30 分钟测量不同来源的字节率、事件率与重放开销，再固定保留配置。建议初始上限：原始记录最长 24 小时，降采样热力最长 7 天，整体磁盘上限 2 GiB；时长和容量先达到者优先清理，实际可用历史以覆盖清单为准。
- 清理前先删除依赖同一段原始记录的失效索引，保留可解释的覆盖边界；热力分区若独立完整则可继续保留。
- 大体积行情分区要在备份界面中明确包含范围，避免现有每 6 小时全量备份无限放大；具体备份策略随容量测量确定。
- 后端尽可能保留源事件；前端 DOM / Tape 批量刷新目标约 10 次/秒，热力按显示像素分桶，避免为每个历史格子建 DOM 元素。
- 首版目标：选中合约端到端展示延迟 P95 不超过本地接收后 250 毫秒，超载后能恢复；这是待压测的验收目标，不是当前已达到的性能承诺。
- 活跃连接、盘口是否连续、最近消息与最近变化分别统计；不能仅因行情清淡没有盘口变化就断言连接已经失效。

## 8. 实施顺序与验收

| 阶段 | 范围 | 完成标准 |
| --- | --- | --- |
| P0 数据契约 | 能力探测、单位与事件分类、独立订阅、会话与缺口、存储测量 | 三类来源样本都能标准化；快照 / 聚合成交 / 逐笔语义可辨；只变盘口而价格不动也能更新 |
| P1 DOM + 成交明细 | 实时阶梯、净变化、过滤、暂停、成交定位、独立 WS；同时开始记录盘口 | 重连无旧盘口冒充实时；成交不重不漏；换周期不复制事件；期货估算明确；现有图表与模拟交易不受影响 |
| P2 热力图 + 同步回放 | 时间价格图、成交气泡、缺口、深度边界、历史查询、统一游标 | 任意可回放时刻的 DOM 与记录一致；时间聚合不放大数量；无未来数据；三个视图保持同一回放状态 |
| P3 增强 | 币安更深订单簿、按需多所比较、大挂量持续时间、吸收候选与提示 | 指标有来源与覆盖门槛；候选可追溯到原始区间，避免把净变化包装成确定的撤单或冰山单 |

P1 已包含三种来源的共同基础；优先用 OKX 样本验证深度完整性、币安样本验证聚合成交、期货样本验证有限档位与估算语义。P2 再将同一数据层接到热力图。

重点验收样例：

1. 只有一档行情时，其他档位始终为未知；零挂量、不可观察、断线三者可区分。
2. OKX 增量缺序后立即作废，取得新快照前不显示有效 DOM、不延伸热力。
3. 币安部分深度的价格离开 20 档范围后标为未知，不误报为撤单。
4. 重复成交、乱序到达、同毫秒多条成交、断线补洞，均可核对编号与总量。
5. 同一加密成交同时服务 10 秒、30 秒及合成周期时，成交列表只有一条来源记录。
6. 期货累计量回落、开盘首快照、未知方向和主连换月均不制造虚假大单。
7. OKX 张数转币、期货合约乘数、最小价位与显示金额均有样本核验。
8. 原始 / 合并视图切换，以及金额 / 数量筛选不改变底层统计总量。
9. 选择历史成交时主图、DOM、Tape 的游标一致；缺少历史盘口时明确提示，不能回退到当前盘口。
10. 热力时间桶延长时代表挂量不随快照条数线性增加；未知区间不参与平均，也不当成零。
11. 固定回放到某时刻后，追加未来数据不改变当时的分位基线和候选事件。
12. 峰值流量、慢客户端、磁盘上限、后台记录停止、刷新与多标签页操作，不阻塞现有 K 线和警报；无法保全的区间明确显示缺口。

## 9. 后续增强的约束

「挂量突然减少」「成交后挂量回补」「成交很大但价格没推进」可以做成可核对的候选事件，但必须保留观察窗口、数量、价格变化、来源和覆盖信息。首版不输出“主力撤单”“确认冰山”“必然吸收”等超出数据能力的结论。

吸收候选须同时考虑可用成交、价格推进幅度和连续有效的盘口；有缺口、仅一档或成交方向不明时降低能力等级或停用。报警能力放到 P3，阈值通过分品种、分时段的历史回放评估后再定。
