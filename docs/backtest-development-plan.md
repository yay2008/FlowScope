# FlowScope 回测功能开发计划

日期：2026-09-14。状态：开发计划，尚未实现。

## 1. 目标与首版边界

建立“持续采集 → 历史数据集 → 按时间回放 → 策略信号 → 模拟成交 → 结果分析”的本地闭环。相同数据版本、策略版本和配置应产生相同订单、成交及资金曲线。

首版默认范围：

- 单用户本地运行，一次回测一个实际交割合约，不自动换月。
- 主图周期支持现有 10 秒、30 秒；首个策略使用 tick 口径 Delta，按已结束 bar 产生信号。
- 保存原始 tick 快照、数据源 10 秒/30 秒 K 线、合约资料；原始行情按实际合约采集一次，供多个周期共享。
- 支持本地历史导入、配置合约持续采集、运行/取消回测、结果查看与 CSV 导出。
- 首版交易模型为单一净持仓、整数手、市价意图订单；买按后续可用卖一、卖按后续可用买一成交，明确手续费及滑点。
- 默认单个后台回测任务，避免争抢实时行情进程资源。

后续范围：限价排队/复杂部分成交、组合与多合约资金管理、自动换月、参数优化、实盘策略执行。TqSdk 快照不能还原交易所逐笔成交顺序或真实挂单队列，首版结果必须注明模拟精度。

示例策略和费用配置用于验收软件行为，不作为交易建议。历史数据下载权限不是本地回放功能的前置条件，可先使用本地导入和人工构造数据开发。

## 2. 当前代码与改造位置

| 当前文件 | 当前职责 | 计划改造 |
| --- | --- | --- |
| `ingest.py` | SDK 单线程采集、Feed 生命周期、聚合和广播 | 将原始采集需求与页面需求分开；复制新增/修订数据交给存储线程 |
| `history_store.py` | 聚合买卖量 CSV、回填、CVD | 保留实时图表兼容；回测通过独立历史读取接口获取指定版本数据 |
| `tick_analytics.py` | 增量 tick 分类、聚合、足迹缓存 | 提供显式状态初始化/恢复，验证分块回放与批量计算一致 |
| `indicator.py` | Lee–Ready、K 线与足迹计算 | 保留并复用核心算法，分离内部原始时间与前端展示时间 |
| `static/app.js` | 图表及部分滚动指标计算 | 将策略所需滚动指标实现到后端，并对照前端固定样例 |
| `app.py` | REST、WebSocket、服务生命周期 | 增加数据集和后台回测任务接口 |
| `tests/` | 分类、周期、数据、Feed、前端同步测试 | 增加存储恢复、回放因果性、模拟成交与完整闭环验收 |

不批量重写现有 CSV，不从旧买卖量 CSV 伪造原始行情。旧数据只保留为图表历史或明确标注的派生参考数据。

## 3. 技术结构与数据约定

### 3.1 模块划分

```text
market_data/
  schema.py          # 字段、时间、版本及数据身份约定
  catalog.py         # SQLite 元数据、文件清单、任务进度
  recorder.py        # 原始行情增量提取及持久化队列
  archive.py         # Parquet 写入、校验、归档与恢复
  reader.py          # DuckDB 按分区/范围/数据版本读取
  import_history.py  # 本地导入、可选 TqSdk 下载适配
  quality.py         # 覆盖、缺口、冲突与数据质量报告
backtest/
  events.py          # 事件结构与顺序
  replay.py          # 按事件时间回放、预热和状态恢复
  features.py        # 后端滚动指标
  strategy.py        # 策略接口和 Delta 示例策略
  execution.py       # 成交规则、费用与滑点
  portfolio.py       # 持仓、资金和逐日结算
  runner.py          # 任务进程、取消、结果发布
  reports.py         # 绩效与导出
static/
  backtest.html
  backtest.js
```

文件名作为职责建议，可在实现时合并小模块。新增运行依赖以 `pyarrow`、`duckdb` 为主；SQLite 使用 Python 标准库。实际兼容版本在第一阶段验证后固定。

### 3.2 存储布局

```text
data/
  catalog.sqlite
  spool.sqlite
  raw/ticks/symbol=<实际合约>/trading_day=<交易日>/part-<id>.parquet
  raw/klines/symbol=<实际合约>/period=<秒>/trading_day=<交易日>/part-<id>.parquet
  derived/algorithm=<版本>/dataset=<版本>/period=<秒>/...
  backtests/<run_id>/
    config.json
    manifest.json
    orders.parquet
    trades.parquet
    equity.parquet
    metrics.json
```

- SQLite 缓冲库负责事务性追加；目录库负责文件清单、归档水位、数据版本、合约资料和回测状态。
- 回测只读取已发布数据集所引用的不可变文件，不把正在写入的数据混入同一次运行。
- 历史文件只追加新分片；合并/修订生成新文件与新清单。已有回测引用的文件不得提前删除。
- 归档协议：缓冲已提交 → 写同目录临时文件 → 校验并完成文件持久化 → 原子改名 → 提交目录清单 → 清理已归档缓冲。跨库操作以唯一批次号和幂等恢复实现，不假设两个 SQLite 库可以共同原子提交。
- 默认约每秒或累计 1,000 条提交缓冲，以先到为准；约每 5 分钟归档一个分片，收盘后合并。阈值经基准测试调整。
- 明确默认最多约一个提交批次的未提交数据可能在进程异常时丢失；已提交记录必须可以恢复。断电耐久性取决于同步设置及文件系统，不能宣称零丢失。
- 使用有界队列；持续写入失败或队列溢出必须进入异常状态并记录可能缺口，禁止静默丢弃。

### 3.3 必须固定的字段及语义

| 数据 | 关键字段与约定 |
| --- | --- |
| Tick | `symbol`、`event_ts_ns`、`received_ts_ns`、`trading_day`、源序号（可空）、采集会话、接收序号、最新价、买卖一价及量、累计成交量、成交额、持仓量、来源、修订号 |
| K 线 | 合约、周期、开始/结束时间、OHLC、成交量、持仓量、可用时间、是否结束、来源、修订号 |
| 合约资料 | 价位步长、乘数、交易日历/时段、到期日、资料生效区间、来源；主力映射独立保存 |
| 质量 | 区间、缺口类型、发现依据、补数状态、来源；分别描述采集连续性和 bar 成交量核对结果 |
| 运行配置 | 数据清单及哈希、策略/算法/代码版本、参数、预热范围、CVD 起点、覆盖策略、费用/滑点/保证金配置、时间与事件排序规则 |

时间保存为 UTC 纳秒整数，交易日按交易日历另存，展示时才做时区转换。现有 `TZ_SHIFT_S` 不进入新原始存储层。通过适配器维持现有图表时间协议。

不单独用时间戳去重。第一阶段先实测 TqSdk 序号在重连、跨日、实时和历史导入之间的语义；源序号不是未经验证的全局主键。保存来源与会话信息，无法可靠匹配的重复候选保留并标记，不猜测删除。

金额/成交计算采用明确的小数精度或整数价位单位，结果导出时记录舍入规则；未知值保存为空，不能填零掩盖缺失。

## 4. 分阶段开发任务与验收

工期按一名熟悉 Python/前端的开发者估算，共 19–27 个工作日；不包含等待交易日采样和外部数据授权的时间。阶段工期是实现预算，不是已验证性能或交付承诺。

### P0：协议和样本验证（1–2 天）

任务：

1. 确认原始字段、SDK 序号、时间戳和夜盘交易日，采集不含凭据的小样本。
2. 确认 SDK 历史 K 线、实时 K 线修订的可用时间处理。
3. 固定数据集清单、事件顺序、去重/修订、质量和回测配置结构。
4. 确定目标样本合约及历史区间；默认验收规模为一个实际合约、至少 20 个交易日，数据不足时用构造数据先验证逻辑。
5. 固定依赖兼容版本，运行已有 Python 和 JavaScript 检查建立基线。

验收：字段文档、脱敏样本和预期事件输出落库；同时间多 tick、夜盘跨日、累计量重置、重连重叠都有明确预期。若序号语义无法确定，降级为保留原始观测并标记冲突的方案，不阻断后续。

### P1：可恢复的历史存储（3–4 天）

任务：实现 schema、SQLite 缓冲/目录、Parquet 归档、DuckDB 分块读取、不可变数据集发布和恢复命令。

验收：

- 完成写入 → 归档 → 重启 → 范围读取，字段和顺序一致。
- 在归档每一步注入异常，恢复后已提交记录不丢失，已发布数据集无逻辑重复；孤立文件可识别和回收。
- 跨交易日和多分片查询正确，修订数据集不改变旧版本读取结果。
- 读取以批次为单位，不一次把全部历史载入内存；测量每百万条存储量、写入/读取耗时及峰值内存。

### P2：独立采集、补数与质量（3–4 天）

任务：

1. 改造 `ingest.py`，增加配置驱动的采集合约集合，独立于页面 Feed 闲置回收。
2. 同一实际合约只记录一份原始 tick；采集线程只读取 SDK 活引用并复制快照，存储线程不得访问 SDK 活对象。
3. 记录 K 线更新和最终状态，保留实时可用时间；记录断线、异常、重连和可疑缺口。
4. 实现单合约本地 CSV/Parquet 导入及质量报告。TqSdk `DataDownloader` 作为可选适配器，下载后走同一校验发布流程。
5. 补数任务按合约/日期记录状态，可中断恢复。补入数据生成新版本，区分实时观测与事后历史修订。
6. 增加采集状态和数据可用区间查询。

验收：关闭所有页面后配置合约仍采集；同时打开 10 秒/30 秒图表不重复保存；重启和断线后可继续；累计量重置不产生负成交量；正常休市不被误判成缺口。存储故障会反映到状态接口，已有图表功能通过回归检查。

### P3：确定性行情回放及指标（3–5 天）

任务：

1. 建立 `MarketDataReader` 和 `ReplayEngine`，按固定事件顺序流式读取指定数据集。
2. 复用 `indicator.py` 和 `TickAnalytics` 的判向状态，抽离前端展示时间转换。
3. 加入预热、CVD 起点和交易日状态处理；历史按块读取时传递前序判向状态。
4. 实现后端策略所需 rolling 指标，首版 Delta 策略优先；LSMA/CRVOL 在固定前端样例上做对照，为扩展策略准备。
5. 输出行情事件和 bar 结束事件，提供命令行回放及派生缓存。

事件规则：

- 订单只匹配产生信号之后的可用行情事件；同时间戳用稳定序号确定先后，无法确定则按保守规则处理并记录。
- 使用已结束 bar 产生信号；晚到修订不允许改写已经执行的历史交易。
- 原始实时观测可提供按接收顺序回放；历史下载通常只有最终数据，使用明确标记的历史事件模式。最终数据发布的 bar 至早在结束之后可用，不声称精确复刻当时的到达顺序。
- 不把已包含未来记录的 `HistoryStore` CVD 前缀或完整 DataFrame 暴露给策略。
- 首版默认阻止明确缺口区间产生新订单，持仓在缺口期间保持、恢复后按后续行情处理；tick 与 K 线量不一致的 `partial` 单独统计，并提供显式允许估算配置。不能把“量不一致”直接等同“采集缺失”。

验收：全量与任意分块回放的分类/聚合结果一致；相同配置重复运行一致；改变未来输入不改变过去信号；跨日和接缝不丢状态；预热不计交易、不污染正式统计。默认覆盖策略可能无交易时，应返回原因而非伪造结果。

### P4：策略、撮合和账户（4–5 天）

任务：

1. 定义 `on_bar(context, bar)` 策略接口，context 仅可读取当前及过去数据。
2. 实现可配置 Delta 示例策略：超过正阈值目标 +1 手，低于负阈值目标 -1 手，其余保持；阈值仅用于功能演示。反手拆成先平后开。
3. 实现市价意图订单、撤销/拒绝状态、下一可用报价撮合。报价缺失或对手量为零时不成交；首版要求整笔订单不超过可见对手量，否则等待后续报价。同一快照共享成交额度，禁止重复使用盘口量。
4. 支持按手/按成交额费用、开平及平今费用配置、固定整数 tick 滑点。对价格限制和未知盘口明确拒绝/等待行为。
5. 实现合约乘数、持仓成本、已实现/浮动盈亏、权益、保证金占用及开仓资金校验。保证金参数按日期可配置并冻结到运行配置。
6. 加入历史结算价及逐日结算；结算价缺失时只能运行明确标注的按市值估值模式，不冒充交易所结算或历史真实风控。资金不足拒开；低于维持要求记录风险事件并停止新增风险，自动强平策略留待后续。
7. 回测区间结束默认保留未平仓持仓，分别报告浮盈亏与已平仓结果；可选在区间内最后可用报价平仓，额外标注这一假设，禁止借用区间外数据。
8. 输出收益、最大回撤、成交/交易次数、胜率、费用、风险事件及逐日权益。短样本或零方差时年化指标返回不可用，不强行生成数值。

验收：用可手算序列验证开仓、平仓、反手、平今费用、滑点、资金不足、缺失盘口、结算和期末持仓；总权益与现金/持仓账务勾稽一致；信号事件本身不能成交；未来行情不会影响过去成交。保存完整运行配置、数据清单和结果哈希。

### P5：回测任务接口和页面（3–4 天）

计划接口：

- `GET /api/datasets`：合约、时间范围、版本和质量摘要。
- `GET /api/collection/status`：采集状态、写入积压和最近异常。
- `POST /api/backtests`：校验配置并提交后台任务。
- `GET /api/backtests`、`GET /api/backtests/{id}`：列表、状态、进度和错误。
- `POST /api/backtests/{id}/cancel`：取消运行。
- `GET /api/backtests/{id}/results`：绩效及分页结果。
- `GET /api/backtests/{id}/export`：导出结果。

任务：

1. 使用独立工作进程运行回测，Windows 下采用可导入的启动入口；持久化任务状态，服务重启后将中断任务标记为 interrupted，不显示虚假 running。
2. 任务状态采用 queued/running/completed/failed/cancelled/interrupted；取消检查放在批次边界，只有完整校验后的产物发布为成功结果。
3. 独立回测页面选择实际合约、数据版本、日期、10 秒/30 秒、策略参数、初始资金、费用和滑点。
4. 显示数据覆盖摘要、运行进度、绩效卡片、权益/回撤曲线、成交标记和成交明细；图表与明细按区间分页，不能复用现有 800 根快照限制充当全部回测历史。
5. 空数据、数据缺口、无交易、未平仓和失败状态有明确显示；页面刷新后可继续查看已有任务。

验收：从页面完成选择数据 → 运行 → 查看逐笔交易 → 导出；可取消运行；服务重启后任务状态正确；回测期间实时图表仍能更新；导出的交易与页面一致。

### P6：端到端验收与交付（2–3 天）

- 用一个实际合约至少 20 个交易日完成端到端演练；若真实样本不足，明确标记尚未完成此验收，不用构造数据替代真实规模验收。
- 初始性能验收目标：普通开发机处理 100 万条 tick 的单次 Delta 示例回测不超过 60 秒，工作进程峰值内存不超过 1 GB；记录机器、数据规模、足迹开关和实测值，目标可根据 P1 基准协商调整。
- 运行已有 Python/JavaScript 回归检查及新增关键测试；故障演练涵盖重启、写盘失败、重复导入和数据修订。
- 在 `README.md` 增加采集配置、导入/补数、数据备份、恢复、回测使用及已知限制。
- 提供可重复运行的示例配置、脱敏小样本和期望结果。测试默认离线，不要求真实账户或外部权限。

## 5. 里程碑与实施依赖

```text
P0 协议固定 → P1 存储 → P2 采集和补数 → P3 回放 → P4 交易模拟 → P5 页面 → P6 验收
```

- M1（P2 完成，约第 7–10 个工作日）：关掉页面仍可积累可查询、可恢复的原始历史。
- M2（P4 完成，约第 14–20 个工作日）：命令行完成可复现的策略回测，账务和因果性通过验证。
- M3（P6 完成，约第 19–27 个工作日）：页面可运行、查看、导出，文档及真实样本验收齐全。

每阶段完成后保存检查结果；仅在新改动、失败或未解决问题出现时扩大测试范围。实现阶段可按上述里程碑拆成独立变更，旧图表 CSV 兼容逻辑在新历史服务稳定后再单独评估替换。

## 6. 优先解决的风险

| 风险 | 应对与验收方式 |
| --- | --- |
| 采集受页面生命周期影响 | 独立配置采集需求，覆盖无人访问测试 |
| 同时间/重连/修订造成误去重 | 先确认源身份规则，保留冲突，验证重复导入幂等性 |
| tick 与 K 线来源存在口径差异 | 两者分别保存，质量字段分开，策略显式选择覆盖政策 |
| 历史最终数据引入未来信息 | 固定事件可用时间、禁止提前暴露修订和最终 bar，做未来数据扰动测试 |
| 前后端指标不一致 | 统一后端策略实现，用固定前端样例比对预热和边界 |
| 下载权限不足 | 首先支持本地导入与持续采集，下载适配不阻断回测引擎 |
| 历史费用/保证金/结算资料不完整 | 冻结用户提供的情景参数，报告假设；不声称真实历史成本 |
| 多文件归档中途退出 | 临时文件、批次身份、幂等目录提交及故障恢复验收 |
